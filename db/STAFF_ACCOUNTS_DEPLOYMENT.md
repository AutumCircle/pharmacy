# Сотрудники: миграция 0014

Реализация подготовлена для ветки `codex/staff-accounts`. Скрипт подготовки
работает только с локальными файлами: к AWS/PostgreSQL не подключается.
До применения миграции второй аккаунт в рабочей базе **не существует**.

## Модель доступа

- `account_id=1` сохраняет текущие логин/пароль и просмотр каталога аптеки.
- `account_id=2` входит в систему, но видит «Доступ пока не предоставлен».
- Разрешения фиксированы CHECK-ограничением SQL; создать третий аккаунт или
  изменить разрешения через API нельзя. API удаления аккаунтов отсутствует.
- PBKDF2-HMAC-SHA256: 600000 итераций, случайная соль 128 бит на каждый пароль.
  Старый пароль импортируется без изменения; новые пароли проходят проверку
  длины 6–128 символов. Логины уникальны без учёта регистра.
- Cookie идентифицирует аккаунт и credential_version. Lambda проверяет текущую
  версию в PostgreSQL при каждом защищённом запросе; смена логина/пароля
  увеличивает версию и завершает существующие сеансы. Старые cookie без ID
  аккаунта недействительны: после обновления потребуется повторный вход.
- Изменение реквизитов и запись `staff.credentials.changed` в существующий
  `admin_audit_log` выполняются одной транзакцией. В details только признаки
  изменения логина/пароля; хеши и пароли не возвращаются и не журналируются.
- Пять неверных паролей блокируют известный аккаунт на 15 минут. Счётчик
  хранится в PostgreSQL с блокировкой строки, общий для экземпляров Lambda.

## Подготовка и порядок выкладки (вручную, отдельно от этой задачи)

1. Убедиться, что окружение подготовки содержит **текущие production**
   `STAFF_USERNAME`, `STAFF_PASSWORD`, если они заданы, и `ADMIN_SESSION_SECRET`.
   Без STAFF_USERNAME используется прежний `pharmacy_staff`; без STAFF_PASSWORD
   скрипт воспроизводит прежнее HMAC-вычисление из ADMIN_SESSION_SECRET.
   Нельзя использовать другой session secret: изменится пароль первого аккаунта.
   Локальный артефакт этой задачи подготовлен из `.env.local`; соответствие
   production не проверялось. Сверить конфигурацию перед использованием.
2. Запустить `python scripts/prepare_staff_accounts.py` с этими переменными.
   Скрипт выдаёт новые временные реквизиты один раз и создаёт
   `.staff-bootstrap/0014_prepared.sql`. Пароли в файлы не записываются;
   SQL содержит только хеши. Каталог исключён из Git. Ограничить его доступ
   средствами ОС (на Windows — ACL) и хранить временный пароль в менеджере паролей.
   Скрипт отказывается перезаписывать готовый файл. Для повторной подготовки
   сохранить нужный файл вне репозитория и убрать прежний артефакт вручную.
3. Сделать резервную копию БД и применить подготовленный SQL штатным процессом
   миграций. SQL выполняется атомарно. Обычный файл 0014 требует четырёх настроек
   `vatan.staff1_username`, `vatan.staff1_hash`, `vatan.staff2_username`,
   `vatan.staff2_hash`; подготовленный файл задаёт их внутри транзакции.
   Миграция не предназначена для повторного запуска и сброса изменённых паролей.
4. Развернуть обновлённую **admin-api-v1 Lambda** вместе с shared-модулями.
   Пакетировщик уже включает все shared/*.py, отдельная Lambda не нужна.
   Задать `ADMIN_SESSION_SECRET` (тот же, что в Next.js) и новый независимый
   `STAFF_API_BEARER_TOKEN` длиной минимум 32 символа. Не переиспользовать
   ADMIN_API_BEARER_TOKEN. Не включать логирование тела запросов/ответов и
   заголовков Authorization/x-staff-session в Gateway, Lambda или трассировке.
5. Добавить маршруты Gateway из таблицы ниже. Сохранить x-api-key / usage plan,
   HTTPS, ограничения частоты и размера тела; отдельно ограничить `/staff/login`
   по IP на Gateway/WAF, чтобы ограничивать запросы с неизвестными логинами.
   CORS браузеру не нужен: все обращения проходят через сервер Next.js.
6. Задать на сервере Next.js `API_V1_BASE_URL`, `API_KEY`,
   `STAFF_API_BEARER_TOKEN`, `ADMIN_SESSION_SECRET`; административные настройки
   остаются прежними. В NEXT_PUBLIC_* секреты не добавлять. Развернуть Next.js
   после миграции, Lambda и Gateway. STAFF_USERNAME/STAFF_PASSWORD больше не
   используются приложением; после проверки переноса убрать их из окружения.
7. На staging проверить вход обоих сотрудников, запрет каталога/админки второму,
   изменение реквизитов, отзыв старых cookie, конфликт логинов и аудит.
   Новый временный пароль сменить через «Сотрудники» при передаче аккаунта.

| Метод | Путь | Проверка в Lambda |
|---|---|---|
| POST | `/v1/staff/login` | Отдельный staff service bearer + пароль сотрудника |
| GET | `/v1/staff/session` | Staff service bearer + подписанный x-staff-session + версия в БД |
| GET | `/v1/staff/medicines` | То же + catalog_access |
| GET | `/v1/staff/catalog/stats` | То же + catalog_access |
| GET | `/v1/admin/staff` | Существующая admin authorization |
| PATCH | `/v1/admin/staff/{account_id}` | Существующая admin authorization |

Все шесть маршрутов интегрируются с admin-api-v1 Lambda. Staff-маршруты
не должны использовать authorizer, требующий административную роль. API key
сам по себе не авторизует запрос. Staff bearer не принимается admin-маршрутами.
Тело PATCH: `username` и/или `password`; отсутствующий password сохраняет хеш,
пустой password отклоняется. Ответ содержит ID, логин, доступ, версию и password_set.

## Проверки и ограничения

Локальные focused-тесты используют mock PostgreSQL и не обращаются к AWS.
Команды: `python -m unittest backend.tests.test_staff_accounts
backend.tests.test_authorization backend.tests.test_admin_contract.AdminRouteAuthorizationTests`;
`node --test tests/staff-session.test.ts`; `npm run lint`; `npm run build`.

Дополнительный запуск всего test_admin_contract обнаружил существующую ошибку
в test_banner_title_can_be_empty_for_image_only_banner: KeyError `title_x`.
Она воспроизведена на исходном HEAD до изменений этой задачи. Код баннеров
и этот тест не изменялись.

Production Gateway/Lambda/RDS, IAM, SSL, лимиты, планы SQL, метрики и фактическая
миграция не проверялись. Нужен staging-тест на PostgreSQL для уникального индекса,
CHECK-ограничений и атомарного отката аудита вместе с изменением реквизитов.
При откате Next.js к старой версии вернутся старые env-реквизиты, а не новые
пароли из БД: без согласованного плана такой откат не выполнять. Таблицу
и журнал при откате не удалять.
