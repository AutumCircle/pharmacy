# Pharmacy Vatan V4 — Product Definition

**Status:** Approved v1.0 — product-owner decisions incorporated
**Phase:** 1 — System Definition & Security Audit
**Language of identifiers:** API fields and statuses remain in English; product rules are documented in Russian.

## 1. Назначение продукта

Pharmacy Vatan V4 — MVP интернет-витрины аптеки с заказом лекарств без онлайн-оплаты. Покупатель находит товар, кладёт его в локальную корзину, передаёт контактные данные и адрес, а затем отслеживает заказ по номеру телефона. Администратор управляет категориями и жизненным циклом заказа, а локальный процесс синхронизации обновляет каталог из аптечного источника данных.

Цель MVP — принять корректный заказ по актуальным данным каталога и дать покупателю понятный статус доставки. Цены, доступность, итог заказа, роли и статусы всегда определяются сервером, а не браузером.

## 2. Пользователи и роли

| Роль | Основная задача | Доступ |
|---|---|---|
| Покупатель | Найти товар, оформить заказ, проверить статус | Только публичный каталог и собственные заказы |
| Администратор | Обработать заказ, управлять категориями, смотреть историю | Только после серверной аутентификации и авторизации |
| Оператор синхронизации | Запустить `agent_sync.exe` и проверить результат импорта | Только служебный sync API с отдельной machine identity |
| Система | Рассчитать цену, проверить наличие, сохранить заказ и аудит | Lambda — единственный компонент, который обращается к RDS |

## 3. Границы MVP

### Входит в MVP

- Поиск и просмотр лекарств.
- Просмотр активных категорий и товаров категории.
- Признак «в наличии / нет в наличии».
- Корзина, сохраняемая в `localStorage` текущего браузера.
- Оформление заказа без регистрации и без онлайн-оплаты.
- Оплата наличными курьеру при получении.
- Доставка по адресу после телефонного подтверждения оператором.
- Отслеживание своих заказов по нормализованному номеру телефона.
- Административный список заказов и контролируемое изменение статуса.
- Создание, изменение и отключение категорий; управление составом категории.
- История смены статусов заказа и история синхронизаций каталога.
- Полная синхронизация каталога через `agent_sync.exe` и защищённый служебный API.

### Не входит в MVP

- Онлайн-оплата, возврат платежа и сохранение банковских данных.
- Личный кабинет покупателя и программа лояльности.
- Медицинские рекомендации, диагностика и замена назначенных препаратов.
- Автоматический расчёт маршрута, зон или срока доставки.
- Частичная продажа недоступного заказа без повторного согласования с покупателем.
- Удаление всей базы, всех заказов или архива через production API.
- Баннеры, промо-механики и сложные скидки, пока для них не утверждены отдельные правила.

## 4. Основной путь покупателя

### 4.1 Search → Product → Cart

1. Покупатель вводит не менее двух символов названия лекарства или открывает категорию.
2. Система показывает каноническое название, страну/производителя при наличии, итоговую цену продажи и доступность.
3. Товар с `in_stock=false` можно увидеть как недоступный, но нельзя добавить в корзину.
4. Покупатель добавляет доступный товар и изменяет количество.
5. Корзина хранится в `localStorage` как удобство интерфейса, но не считается доверенным источником цены или наличия.

### 4.2 Cart → Checkout

1. Покупатель проверяет состав корзины.
2. Для оформления он указывает имя, таджикский номер телефона, адрес и необязательный комментарий.
3. Интерфейс показывает ориентировочную стоимость товаров и утверждённое уведомление: **“Delivery fee is calculated and paid directly to the courier upon delivery.”** Русская UI-локализация: **«Стоимость доставки рассчитывается и оплачивается напрямую курьеру при доставке»**.
4. Кнопка оформления доступна, когда ориентировочный товарный subtotal не меньше 50 TJS.
5. В запрос заказа браузер передаёт только идентификационные данные покупателя и для каждой позиции только `medicine_id` и `quantity`.
6. Lambda получает позиции из RDS по `medicine_id`, проверяет доступность и рассчитывает каждую цену с наценкой 5% и товарный subtotal. Стоимость доставки в заказ не добавляется.
7. Если хотя бы одна позиция отсутствует или недоступна, заказ целиком не создаётся; покупатель получает список проблемных `medicine_id`.
8. После успешной транзакции заказ получает уникальный `order_id` и статус `pending`, а телефон сохраняется локально для перехода к tracking.
9. Оператор связывается с покупателем по телефону для подтверждения заказа и адреса.

### 4.3 Tracking via Phone

1. Покупатель вводит тот же номер телефона, который использовал при checkout.
2. Номер нормализуется к формату E.164 (`+992XXXXXXXXX`) и сравнивается только по точному совпадению.
3. Система возвращает только минимальные данные заказов этого номера, отсортированные от новых к старым.
4. Полный телефон и точный адрес не возвращаются в публичном tracking-ответе; чувствительные поля маскируются.
5. Базовые статусы показываются как `pending` → `confirmed` → `delivering` → `delivered`; `cancelled` отображается отдельно.
6. Поиск только по телефону утверждён для MVP. Он защищается rate limiting и не вызывает административный `list_orders`. OTP и связка «номер заказа + телефон» отложены на будущий milestone.

## 5. Путь администратора

### 5.1 Вход и доступ

1. Администратор проходит серверную аутентификацию.
2. Сервер создаёт подписанную, ограниченную по времени `HttpOnly`-сессию.
3. Каждая административная операция повторно проверяет роль на сервере и в Lambda; одного наличия cookie или API key недостаточно.

### 5.2 Заказы

1. Администратор открывает пагинированный список заказов и фильтрует его по статусу/дате.
2. Он видит состав заказа, серверные ценовые snapshots, контакт для обработки и историю статусов.
3. Допустимые переходы:

   - `pending` → `confirmed` или `cancelled`;
   - `confirmed` → `delivering` или `cancelled`;
   - `delivering` → `delivered`;
   - `delivered` и `cancelled` — конечные статусы.

4. Произвольный переход или неизвестный статус отклоняется Lambda.
5. Каждая смена статуса записывается append-only с временем и субъектом изменения.
6. Администратор не изменяет сохранённую цену позиции или итог уже созданного заказа.

### 5.3 Категории

1. Администратор создаёт категорию с уникальным `slug` и названием.
2. Он редактирует отображаемые свойства и включает/отключает категорию.
3. Он добавляет или удаляет связь между категорией и лекарством по `medicine_id`.
4. Удаление используемой категории по умолчанию заменяется мягким отключением (`is_active=false`).
5. Публичный каталог показывает только активные категории и только доступные для продажи товары.

### 5.4 История

- История заказов показывает все переходы статусов, время и администратора/сервис, выполнивший действие.
- История синхронизаций показывает `sync_id`, время, результат, количество обработанных, обновлённых, доступных, архивированных и ошибочных записей.
- История не должна содержать секреты, полные payload с персональными данными или исходные API credentials.

## 6. Бизнес-правила

### 6.1 Цена и наценка 5%

- `base_unit_price` поступает из доверенного каталога и хранится в RDS как точное десятичное значение, не как floating point.
- Каноническая цена одной единицы для покупателя:

  `selling_unit_price = ceil(base_unit_price × 1.05)`

- Округление выполняется вверх до целого TJS для каждой единицы до умножения на количество.
- Примеры: `100.00 → 105`, `100.01 → 106`, `12.10 → 13` TJS.
- `items_subtotal = Σ(selling_unit_price × quantity)`.
- Наценка рассчитывается только в Lambda. Frontend может показывать estimate, но не передаёт и не определяет цену.
- При создании заказа сохраняются snapshots базовой и продажной цены, чтобы последующая синхронизация не меняла исторический заказ.
- Никакие скидки, ручные цены и промокоды не применяются, пока для них не утверждены отдельные правила.

### 6.2 Наличие и правило `*`

- В исходном файле синхронизации один ведущий символ `*` перед названием означает «нет в наличии».
- `*` является служебным маркером, не частью канонического названия: перед сопоставлением имя очищается от одного ведущего `*` и внешних пробелов.
- Строка без ведущего `*` означает `in_stock=true`; строка с ним — `in_stock=false`.
- Товары `in_stock=false` сохраняются для истории и tracking существующих заказов, но не могут быть добавлены в новый заказ.
- Lambda обязательно повторно проверяет `in_stock` внутри транзакции создания заказа.
- Успешный полный snapshot переводит отсутствующие в нём ранее активные товары в `in_stock=false`, но не удаляет их.
- Так как `OSTATKI.DBF` не содержит SKU, fallback-идентичность строится из очищенных и приведённых к одному регистру `NAME + PROIZVOD + COUNTRY`.
- Повторения одного fallback-ключа объединяются детерминированно: доступная строка имеет приоритет перед архивной, затем выбирается максимальная базовая цена, а при равенстве — первая строка DBF. Усреднение цены запрещено. Факт объединения сохраняется в истории синхронизации.
- Если источник в будущем предоставит SKU, повтор одного SKU считается ошибкой и не разрешается автоматическим объединением.

### 6.3 Минимальный заказ, доставка и оплата

- Минимальный subtotal товаров: **50 TJS**. Проверка выполняется Lambda после серверного расчёта цены.
- Аптека не устанавливает, не рассчитывает, не добавляет в заказ и не получает стоимость доставки.
- Стоимость доставки согласовывается напрямую между покупателем и курьером и оплачивается покупателем непосредственно курьеру при доставке.
- `order_total = items_subtotal`; стоимость доставки не является частью `order_total` и не сохраняется как `delivery_fee` заказа.
- Checkout обязан показывать утверждённое уведомление: **“Delivery fee is calculated and paid directly to the courier upon delivery.”** Русская UI-локализация: **«Стоимость доставки рассчитывается и оплачивается напрямую курьеру при доставке»**.
- Доступная география, стоимость и фактический срок доставки согласовываются с курьером; оператор подтверждает заказ и адрес по телефону.
- Единственный метод оплаты MVP — `cash_on_delivery`; онлайн-платёжных данных система не принимает.
- Заказ создаётся как `payment_status=unpaid`; это состояние относится только к стоимости лекарств и не включает отдельную оплату доставки курьеру.

### 6.4 Клиентские данные

- Имя, телефон, адрес, комментарий, содержимое `localStorage`, цена, total и статус считаются недоверенным вводом.
- Телефон принимается как 9 местных цифр или E.164 и сохраняется в одном каноническом формате.
- `localStorage` используется только для корзины, избранного, сохранённого телефона и удобства повторного заполнения; потеря или изменение этих данных не должна повреждать данные сервера.
- Публичный ответ не раскрывает базовую закупочную цену, служебные поля, чужие заказы или немаскированные персональные данные.

### 6.5 Идентичность лекарства

- В API v1 лекарство однозначно определяется неизменяемым положительным целочисленным `medicine_id` — primary key RDS.
- Если источник предоставляет SKU, он хранится отдельно как `source_sku` с уникальным сопоставлением к `medicine_id`; API заказа всё равно принимает только `medicine_id`.
- Название, производитель и дозировка являются отображаемыми данными и не используются как ключ заказа.
- Поиск и каталог обязаны возвращать `medicine_id`; корзина хранит его вместе с display snapshot.
- Checkout передаёт только `medicine_id` и `quantity`. Lambda выполняет lookup только по `medicine_id` и отклоняет отсутствующую или недоступную запись.
- Полный snapshot синхронизации не должен переназначать существующие `medicine_id`. Upsert выполняется по стабильной идентичности источника, а не удалением и повторной вставкой всего каталога.
- В order item сохраняются `medicine_id` и snapshots названия, базовой и продажной цены, чтобы история не зависела от будущих изменений каталога.

## 7. Как `agent_sync.exe` обновляет каталог

Исходный код и бинарный файл `agent_sync.exe` отсутствуют в этом репозитории, поэтому текущая реализация не подтверждена. Ниже зафиксировано утверждённое целевое поведение; фактическую input schema ещё необходимо предоставить перед реализацией sync backend.

1. Агент читает локальный аптечный источник и формирует полный snapshot с уникальным `sync_id`, временем источника и checksum.
2. Агент не получает credentials RDS и не выполняет SQL напрямую.
3. Он аутентифицируется отдельной machine identity и загружает snapshot через защищённый internal API. Для большого файла API выдаёт короткоживущий pre-signed URL в S3.
4. Sync Lambda валидирует схему, цену, название, дубли и правило ведущего `*`, затем помещает данные во временную staging-область.
5. Если критическая валидация не пройдена, production-каталог не изменяется; результат фиксируется как failed.
6. При успешной проверке Lambda одной транзакцией upsert-ит товары с сохранением стабильных `medicine_id`, обновляет `base_unit_price` и `in_stock`, архивирует отсутствующие позиции по утверждённому правилу и сохраняет sync history.
7. Ручные категории и исторические price snapshots заказов синхронизация не перезаписывает.
8. Повторная отправка того же `sync_id` идемпотентна и не запускает второй импорт.
9. Cleanup, wipe и физическое удаление строк не являются частью обычной синхронизации.

Целевой поток: `local source → agent_sync.exe → internal API/S3 → sync Lambda → RDS PostgreSQL`.

## 8. Карта текущего состояния

Статусы: **готова** — соответствует MVP; **частично** — поток существует, но контракт/защита неполны; **mock** — интерфейс без production data path; **отсутствует** — реализация не найдена; **небезопасна** — поток нельзя выпускать в production в текущем виде.

| Функция | Сейчас | Цель Phase 2 |
|---|---|---|
| Поиск и получение лекарства | Частично | Строгие public routes, валидация и пагинация |
| Корзина в `localStorage` | Частично | Оставить как UX-state; никогда не доверять цене/наличию |
| Наценка 5% | Небезопасна | Единственная каноническая реализация в Lambda |
| Checkout | Небезопасна | Передавать `medicine_id`/quantity, удалить клиентские `price`/`total`, добавить серверный расчёт и idempotency |
| Tracking по телефону | Небезопасна | Узкий public lookup вместо административного `list_orders` |
| Публичные категории | Mock | Подключить public categories API |
| Управление категориями | Частично | Admin auth в handler/Lambda, строгие схемы и soft delete |
| Список и статусы заказов | Частично/небезопасна | Пагинация, серверная роль, state machine и audit trail |
| История синхронизаций | Частично | Структурированный результат каждого `sync_id` |
| `agent_sync.exe` | Не подтверждено | Защищённая атомарная синхронизация только через Lambda |
| Баннеры | Mock, вне core MVP | Отложить до отдельного контракта |
| Destructive actions | Небезопасна | Не маршрутизировать в production; отдельная аварийная процедура |

## 9. Security gates и управление ключами

- Текущая локальная конфигурация и существующий development `API_KEY` остаются активными на Phase 2; ротация выполняется на финальном production deployment.
- Во время разработки запрещено добавлять ключ в новые client-side payloads, логи или browser bundle. `NEXT_PUBLIC_API_KEY` не допускается в production; секреты доступны только server-side runtime.
- Перед production release выпускается новый ключ, переключается server-side environment, проверяется отсутствие старого ключа в runtime, после чего старый ключ отзывается.
- Удалить fallback admin password и заменить константную cookie на проверяемую серверную сессию.
- Закрыть legacy action router deny-by-default и убрать из production routing `wipe_db`, `delete_all_orders`, `cleanup_archive` и любые неизвестные actions.
- Не запускать `wipe-db.py` или другие mutation diagnostics при проверке.
- Разделить public, admin и internal sync permissions на уровне API Gateway, Lambda handlers и IAM.
- Добавить rate limits, structured audit logs, request IDs и алерты на ошибки/подозрительные запросы.

## 10. Критерии готовности MVP

- Покупатель может найти доступный товар, оформить cash-on-delivery заказ и увидеть его статус.
- Payload `create_order` не содержит цены, subtotal, delivery fee, total, статуса или роли.
- Сервер получает товар только по `medicine_id` и отклоняет неизвестный/недоступный ID или неверное количество.
- Один повторённый checkout с тем же idempotency key создаёт не более одного заказа.
- Tracking не загружает все заказы и не раскрывает чужие персональные данные.
- Только авторизованный администратор может читать все заказы и менять допустимые статусы.
- Синхронизация либо публикуется целиком, либо не меняет каталог; результат виден в истории.
- Ни один production route не предоставляет массовое удаление базы, архива или заказов.

## 11. Утверждённые решения владельца

1. Минимальный товарный subtotal — **50 TJS**; заказ на меньшую сумму не создаётся.
2. Аптека не рассчитывает и не получает плату за доставку; она согласовывается и оплачивается напрямую курьеру и не входит в order total.
3. Наценка рассчитывается как `ceil(base_unit_price × 1.05)` для каждой единицы товара.
4. API v1 и корзина используют `medicine_id`; `medicine_name` остаётся display snapshot.
5. Phone-only tracking с rate limiting используется в MVP; OTP отложен на будущий milestone.
6. Canonical status flow и запрет отмены после `delivering` без отдельной аварийной роли сохраняются.
7. Отсутствующий из успешного полного snapshot товар становится `in_stock=false`, но физически не удаляется.
